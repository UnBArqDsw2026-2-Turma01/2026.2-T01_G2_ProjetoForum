# 3. Engenharia Reversa - Fluxo de Login do TabNews

## Autenticação, Cadastro e Recuperação de Senha

> Arquitetura e Desenho de Software - UnB | Evidências coletadas em 26/08/2026

---

## 1. Introdução

A presente análise de engenharia reversa foi realizada a partir da observação do site **TabNews** (tabnews.com.br), com foco na página de login ([https://www.tabnews.com.br/login](https://www.tabnews.com.br/login)) e nos fluxos diretamente acessíveis a partir dela: cadastro de novo usuário e recuperação de senha.

Foram analisados três grupos principais:

- formulário e comportamento da página de login;
- cadastro de novo usuário;
- recuperação de senha.

A análise buscou identificar o comportamento apresentado ao usuário, os fluxos existentes, os requisitos funcionais observáveis e as regras de negócio explicitadas pela plataforma.

Os requisitos foram descritos utilizando a estrutura **"O sistema deve..."**, buscando manter cada requisito claro, específico e verificável. Regras e condições foram registradas separadamente como regras de negócio.

### 1.1 Metodologia e diferenças em relação a análises anteriores

Diferentemente de uma engenharia reversa apoiada em navegação interativa e captura de tela (*screenshots*), esta análise foi conduzida por meio de:

- obtenção do conteúdo renderizado das páginas de login, cadastro e recuperação de senha via requisição HTTP direta;
- consulta ao repositório público do TabNews no GitHub (o projeto é *open source*), utilizada apenas para corroborar comportamentos de backend já sinalizados na interface (como o limite de requisições);
- consulta a artigos técnicos publicados por membros da comunidade descrevendo a API pública do TabNews.

> **Limite da análise:** não foi utilizada automação de navegador nem captura de tela nesta análise, portanto o documento não contém figuras. Elementos que dependem de renderização visual (cores exatas, animações, disposição fina de layout) e testes interativos de acessibilidade (navegação por teclado, zoom 200%) não puderam ser verificados diretamente e não constam neste documento.

---

## 2. Login

A Decathlon e outras plataformas de e-commerce costumam expor a autenticação como uma etapa dentro do fluxo de compra. No TabNews, o login é uma página dedicada e independente (`/login`), sem vínculo com carrinho ou checkout, já que a plataforma é uma comunidade de conteúdo, não uma loja.

### 2.1 Formulário de login e verificação de segurança

Ao acessar a página de login, foi observado que o texto **"Executando verificação de segurança..."** é exibido antes do formulário ficar disponível. Após essa verificação, o formulário apresenta os campos "Seu Email" e "Senha", uma opção "Visualizar Senha" e o botão "Login".

Abaixo do formulário, a página oferece dois desvios de fluxo: "Novo no TabNews? Crie sua conta aqui." e "Esqueceu sua senha? Clique aqui."

**Fluxo observado**

```
Acessar /login → Verificação de segurança → Exibição do formulário → Informar e-mail e senha → Submeter → Autenticação
```

**Requisitos funcionais identificados**

| ID | Requisito |
|---|---|
| RF01 | O sistema deve exibir um indicador de verificação de segurança antes de disponibilizar o formulário de login. |
| RF02 | O sistema deve solicitar o e-mail do usuário no formulário de login. |
| RF03 | O sistema deve solicitar a senha do usuário no formulário de login. |
| RF04 | O sistema deve permitir que o usuário alterne a visualização da senha digitada (mostrar/ocultar). |
| RF05 | O sistema deve permitir que o usuário sem conta acesse o fluxo de cadastro a partir da página de login. |
| RF06 | O sistema deve permitir que o usuário acesse o fluxo de recuperação de senha a partir da página de login. |

> **Observação encontrada:** a mensagem "Executando verificação de segurança..." aparece de forma padronizada em outras páginas do site que também usam formulários (cadastro e recuperação de senha), sugerindo um mecanismo comum de proteção (por exemplo, anti-bot) aplicado à camada de formulários. Como o mecanismo interno não é observável a partir da interface, ele foi registrado apenas como observação, não como regra de negócio.

### 2.2 Autenticação via API

O TabNews é um projeto de código aberto e disponibiliza publicamente a documentação de uso de sua API em seu repositório e em conteúdos publicados pela própria comunidade de usuários. Segundo essas fontes, o envio do formulário de login resulta em uma requisição HTTP do tipo `POST` para o endpoint `/api/v1/sessions`, contendo e-mail e senha no corpo da requisição.

Em caso de sucesso, a resposta da API inclui um token de sessão, que passa a ser utilizado para autenticar as próximas requisições do usuário autenticado.

**Fluxo observado (autenticação)**

```
Formulário de login → POST /api/v1/sessions {email, password} → Validação das credenciais → Token de sessão retornado → Sessão autenticada
```

**Requisitos funcionais identificados**

| ID | Requisito |
|---|---|
| RF07 | O sistema deve autenticar o usuário a partir do e-mail e da senha informados, por meio de uma requisição à API de sessões. |
| RF08 | O sistema deve retornar um token de sessão ao usuário quando a autenticação for bem-sucedida. |
| RF09 | O sistema deve utilizar o token de sessão retornado para autenticar as requisições subsequentes do usuário. |

### 2.3 Proteção contra enumeração de usuários e limite de requisições

A documentação pública do projeto (*Pull Request* de implementação de *rate limit*, disponível no repositório oficial) indica que a rota `POST /api/v1/sessions` possui um limite de requisições mais restritivo do que o limite geral aplicado às demais rotas da API, com uma janela de *cooldown* maior.

A mesma fonte relata que, quando esse limite é atingido, a resposta apresentada ao usuário simula uma falha de login comum, inclusive gerando novos identificadores (`uuid`) de `request_id` e `error_id` a cada tentativa, da mesma forma como ocorreria em uma tentativa de login malsucedida por credenciais inválidas. Esse comportamento tem como objetivo evitar que um atacante identifique se está sendo bloqueado por limite de requisições ou se as credenciais testadas estão erradas.

**Requisitos funcionais identificados**

| ID | Requisito |
|---|---|
| RF10 | O sistema deve aplicar um limite de requisições específico para a rota de autenticação, mais restritivo do que o limite geral por IP aplicado às demais rotas. |
| RF11 | O sistema deve apresentar, ao atingir o limite de requisições de login, uma resposta equivalente à de uma tentativa de login malsucedida, sem indicar de forma explícita que o bloqueio ocorreu por limite de requisições. |

**Regras de negócio identificadas**

| ID | Regra de negócio |
|---|---|
| RN01 | O limite de requisições da rota de sessão (login) é mais baixo e possui janela de *cooldown* maior do que o limite geral por IP das demais rotas da API. |
| RN02 | Respostas de bloqueio por limite de requisições na rota de login reutilizam a mesma estrutura de erro de uma falha de autenticação comum, incluindo novos identificadores a cada tentativa, como medida de segurança contra ataques de enumeração de credenciais. |

## 3. Cadastro de novo usuário

A partir do link "Crie sua conta aqui." exibido na página de login, o usuário é direcionado para `/cadastro`. Assim como a página de login, essa página também exibe a mensagem de verificação de segurança antes do formulário ser disponibilizado.

O formulário de cadastro apresenta os campos "Nome de usuário", "Seu Email" e "Senha", além de uma opção para visualizar a senha digitada. Também é exibida uma declaração de concordância obrigatória com os Termos de Uso, com link para o documento completo, antes do botão "Criar cadastro".

**Fluxo observado**

```
Login → "Crie sua conta aqui" → /cadastro → Verificação de segurança → Preencher usuário, e-mail e senha → Aceitar Termos de Uso → Criar cadastro
```

**Requisitos funcionais identificados**

| ID | Requisito |
|---|---|
| RF12 | O sistema deve solicitar um nome de usuário durante o cadastro. |
| RF13 | O sistema deve solicitar um e-mail durante o cadastro. |
| RF14 | O sistema deve solicitar uma senha durante o cadastro. |
| RF15 | O sistema deve permitir que o usuário alterne a visualização da senha digitada durante o cadastro. |
| RF16 | O sistema deve exigir a concordância explícita do usuário com os Termos de Uso antes de permitir a criação do cadastro. |
| RF17 | O sistema deve disponibilizar acesso ao texto completo dos Termos de Uso a partir da tela de cadastro. |

> **Observação encontrada:** o envio do formulário de cadastro não foi executado durante esta análise (não foi criada uma conta real), portanto não foram coletadas evidências sobre a resposta da API de cadastro, sobre eventual etapa de confirmação de e-mail no ambiente de produção, ou sobre mensagens de erro para e-mails/usuários já existentes. Esses itens não foram transformados em requisitos.

## 4. Recuperação de senha

A partir do link "Esqueceu sua senha? Clique aqui." na página de login, o usuário é direcionado para `/cadastro/recuperar`. A página exibe, após a verificação de segurança, um único campo ("Digite seu e-mail") e o botão "Recuperar".

**Fluxo observado**

```
Login → "Esqueceu sua senha? Clique aqui" → /cadastro/recuperar → Verificação de segurança → Informar e-mail → Recuperar
```

**Requisitos funcionais identificados**

| ID | Requisito |
|---|---|
| RF18 | O sistema deve permitir que o usuário solicite a recuperação de senha informando apenas o e-mail cadastrado. |

> **Limite da análise:** não foi realizada a submissão do formulário de recuperação de senha, para evitar o disparo de e-mails reais ou o consumo do limite de requisições da conta utilizada na análise. Por esse motivo, não foram inferidos requisitos sobre o conteúdo do e-mail de recuperação, o prazo de validade do link enviado, ou o fluxo de definição de nova senha.

## 6. Regras de negócio identificadas (resumo)

| ID | Regra de negócio |
|---|---|
| RN01 | O limite de requisições da rota de login é mais restritivo que o limite geral por IP das demais rotas. |
| RN02 | O bloqueio por limite de requisições na rota de login não é diferenciado de uma falha comum de autenticação, por questão de segurança. |
| RN03 | A criação de conta exige concordância prévia com os Termos de Uso. |
| RN04 | A recuperação de senha é solicitada apenas com o e-mail do usuário, sem exigir outros dados de identificação nesta etapa inicial. |

---

## 7. Observações encontradas

- As três páginas analisadas (login, cadastro e recuperação de senha) compartilham o mesmo padrão de "verificação de segurança" antes de exibir o formulário, sugerindo um componente reutilizado entre esses fluxos.
- Diferentemente do site da Decathlon, que oferece login social (Google, Facebook e Apple) além do e-mail, não foi identificada, nas páginas analisadas, nenhuma opção de autenticação via provedores externos no TabNews — apenas e-mail e senha.
- O TabNews, por ser um projeto de código aberto, permite corroborar, por meio do próprio repositório público, comportamentos de segurança do backend (como o *rate limit* específico da rota de sessão) que normalmente não seriam observáveis apenas pela interface — uma diferença metodológica relevante frente à engenharia reversa de uma plataforma de código fechado como a Decathlon.

---

## 8. Limitações da análise

- Não houve captura de tela nem uso de navegador automatizado; a análise se baseou no conteúdo textual/HTML retornado pelas páginas e em fontes públicas secundárias (GitHub e artigos da comunidade).
- Não foram submetidos formulários reais de login, cadastro ou recuperação de senha, portanto não há evidência direta de mensagens de erro, validações de campo ou telas pós-submissão.
- Não foi possível realizar testes de acessibilidade (navegação por teclado, zoom de página) nesta análise, diferentemente do que foi feito na engenharia reversa da Decathlon.
- Assim como na análise da Decathlon, não foram inferidos componentes internos, bancos de dados ou algoritmos que não puderam ser diretamente observados ou corroborados por fonte pública confiável.

---

## 9. Conclusão

A engenharia reversa do fluxo de login do TabNews mostrou uma abordagem de autenticação mais simples do que a observada no site da Decathlon: um único método de autenticação (e-mail e senha), sem login social, e uma página dedicada e desacoplada de qualquer fluxo de compra, coerente com a natureza do TabNews como plataforma de conteúdo e comunidade.

Por outro lado, a análise evidenciou um cuidado explícito com segurança da autenticação, expresso tanto na interface (verificação de segurança antes da exibição dos formulários) quanto em mecanismos de backend documentados publicamente, como o limite de requisições reforçado na rota de sessão e a simulação deliberada de respostas de erro para dificultar ataques de enumeração de credenciais.

A separação entre requisitos funcionais e regras de negócio permitiu representar com maior precisão o comportamento observado. Os requisitos descrevem funcionalidades executadas ou disponibilizadas pelo sistema, enquanto as regras de negócio descrevem condições e restrições que determinam quando essas funcionalidades podem ocorrer.

**Fonte das evidências:** site do TabNews ([tabnews.com.br/login](https://www.tabnews.com.br/login), [/cadastro](https://www.tabnews.com.br/cadastro) e [/cadastro/recuperar](https://www.tabnews.com.br/cadastro/recuperar)), repositório público do projeto no GitHub ([github.com/filipedeschamps/tabnews.com.br](https://github.com/filipedeschamps/tabnews.com.br)) e artigos técnicos publicados pela comunidade do TabNews descrevendo sua API, consultados em 26/08/2026.
