# BPMN: Gitflow

## Introdução

O **Gitflow** é um modelo de ramificação (*branching model*) para o Git, proposto por Vincent Driessen em 2010, amplamente adotado em projetos de desenvolvimento de software por organizar de forma clara e previsível o ciclo de vida do código e das alterações realizadas no projeto.

Seu principal objetivo é separar o trabalho em andamento do conteúdo estável, definindo branches com papéis bem determinados: `main`, `develop`, `docs` e `release`. Essa separação permite que múltiplos integrantes colaborem em paralelo sem interferir uns nos outros, mantendo a branch principal sempre em estado estável para as entregas do projeto.

Durante as próximas etapas de desenvolvimento deste projeto, o Gitflow será utilizado como fluxo padrão de trabalho para a produção e manutenção da documentação. Toda nova alteração na documentação partirá de uma branch `docs` criada a partir da `develop`; ao ser concluída e revisada, será integrada de volta à `develop`. Quando o conjunto de alterações estiver estável e pronto para entrega, uma branch `release` será gerada para os ajustes finais e, após aprovação, integrada à `main` com a devida tag de versão. Os integrantes que participaram da criação deste documento podem ser vistos na Tabela 1.

## Descrição do fluxo

### 1. Integrante

O processo se inicia com o integrante criando uma branch `docs` a partir da `develop`. Em seguida, a documentação é elaborada ou atualizada localmente, seguindo os padrões definidos para o projeto. Após a conclusão das alterações, o integrante revisa o conteúdo e envia as modificações ao repositório remoto, abrindo um **Pull Request (PR)** para a branch `develop`.

Caso o revisor solicite ajustes, o integrante realiza as correções necessárias na documentação e atualiza o PR. O ciclo se repete até que as alterações sejam aprovadas.

### 2. Revisor

Ao receber a notificação do PR, o revisor analisa as alterações realizadas na documentação, verificando sua organização, clareza, padronização e conformidade com as diretrizes do projeto. O gateway de decisão **"Aprovado no review?"** determina o caminho seguinte:

* **Não aprovado:** o revisor solicita ajustes por meio de comentários no PR, e o fluxo retorna ao integrante responsável pela documentação.

* **Aprovado:** o merge das alterações para a branch `develop` é realizado.

Após o merge, um segundo gateway verifica se o estado atual da `develop` representa uma **versão estável para release**:

* **Sim:** uma release é gerada, iniciando o processo de publicação na branch `main`.

* **Não:** o fluxo retorna ao início, aguardando novas alterações na documentação.

### 3. main

Ao receber a release gerada após a aprovação das alterações, a branch `main` recebe o merge da versão estável da documentação. Em seguida, é criada a **tag de versão** correspondente à entrega e realizada a publicação da documentação.

O processo encerra com a versão atualizada da documentação disponível para consulta.

Tabela 2: Elementos BPMN utilizados

| Elemento                | Tipo                         | Descrição                                                                                                                                                                                                           |
| ----------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Círculo simples         | Evento de início             | Marca o ponto de partida do processo de atualização da documentação.                                                                                                                                                |
| Círculo com borda dupla | Evento de fim                | Indica o encerramento do processo após a publicação da documentação.                                                                                                                                                |
| Círculo com seta        | Evento intermediário de link | Conecta fluxos distantes sem a necessidade de utilizar setas longas, facilitando a organização visual do diagrama.                                                                                                  |
| Retângulo arredondado   | Tarefa (*Task*)              | Representa uma atividade executada por um participante, como criar, revisar ou publicar a documentação.                                                                                                             |
| Losango com X           | Gateway exclusivo            | Ponto de decisão: apenas um caminho é seguido de acordo com a condição estabelecida. Também pode atuar como ponto de convergência, em que, independentemente do caminho de chegada, a próxima tarefa é obrigatória. |
| Seta tracejada          | Fluxo de mensagem            | Representa a comunicação entre participantes (pools) diferentes.                                                                                                                                                    |
| Seta contínua           | Fluxo de sequência           | Representa a ordem de execução das atividades dentro de um mesmo participante.                                                                                                                                      |
